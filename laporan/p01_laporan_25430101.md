## 1. Tujuan Praktikum
Pada modul 1 ini, terdapat beberapa kompetensi utama yang harus dicapai:
1. Mampu menjalankan serta menghentikan layanan basis data MariaDB melalui XAMPP Control Panel secara aman.

5. Menggunakan Git dan GitHub sebagai media pencatatan versi (*version control*) dan pelaporan berkas praktikum secara berkesinambungan.

## 2. Ringkasan Dasar Teori
MariaDB adalah salah satu *Relational Database Management System* (RDBMS) berbasis open-source yang menerapkan model arsitektur klien-server. Server berjalan sebagai proses latar belakang (*daemon/service*) yang mendengarkan permintaan query pada port standar (default TCP 3306). 

Untuk berinteraksi dengan server basis data, pengguna dapat memanfaatkan dua jenis klien:
* **Klien Baris Perintah (CLI)**: Sangat efisien, dapat disimpan dalam bentuk skrip otomatis (`.sql`), serta menampilkan galat secara presisi.
* **phpMyAdmin**: Klien berbasis web yang memudahkan pengelolaan secara visual, namun memiliki kerentanan keamanan jika mode autentikasinya tidak dikonfigurasi dengan tepat.

Selain itu, pengelolaan akun pada MariaDB diidentifikasi melalui pasangan format `'user'@'host'` yang memungkinkan isolasi hak akses secara granular demi menjaga integritas dan keamanan data.

## 4. Jawaban Titik Analisis

### Titik Analisis 1
**Soal:**  
Label tombol bertuliskan "MySQL", tetapi yang berjalan adalah MariaDB. Apa konsekuensinya ketika Anda mencari solusi galat di internet? Kapan dokumentasi MySQL masih relevan, dan kapan Anda harus merujuk ke dokumentasi MariaDB?

**Jawaban:**  
Konsekuensinya adalah kita harus kritis dalam memfilter solusi permasalahan di internet agar tidak menerapkan solusi atau parameter konfigurasi yang hanya berlaku khusus pada mesin MySQL. Dokumentasi MySQL tetap relevan untuk sintaks standar SQL umum (seperti `SELECT`, `INSERT`, `UPDATE`, operasi JOIN biasa, pembuatan indeks standar, dan tipe data dasar ANSI SQL). Namun, ketika menghadapi masalah mesin penyimpanan (*storage engine* bawaan seperti Aria), pengelolaan sistem autentikasi/plugin pengguna, pengaturan parameter berkas konfigurasi `my.ini`, serta fitur lanjutan seperti replikasi dan perlakuan JSON, kita wajib merujuk secara langsung pada dokumentasi resmi MariaDB.

### Titik Analisis 2
**Soal:**  
Keluar lagi, lalu coba masuk dengan `mysql -u root` tanpa `-p`. Catat pesan galat yang muncul. Bagian mana dari pesan itu yang memberi tahu bahwa klien tidak mengirim password? Bandingkan jawaban Anda dengan Gambar 1.10 di bagian Troubleshooting.

**Jawaban:**  
Pesan galat yang muncul saat mencoba masuk tanpa parameter `-p` adalah:  
`ERROR 1045 (28000): Access denied for user 'root'@'localhost' (using password: NO)`  
Bagian dari pesan yang secara eksplisit memberitahukan bahwa klien tidak menyertakan kata sandi saat permintaan koneksi dikirim adalah frasa **`(using password: NO)`**. Sebaliknya, apabila kata sandi dikirim namun salah, klausa tersebut akan berubah menjadi **`(using password: YES)`**.

### Titik Analisis 3
**Soal:**  
Mengapa `information_schema` tetap terlihat oleh `mhs_101`, sedangkan `mysql` ditolak dengan ERROR 1044? Apa bedanya kode galat 1044, 1045, dan 1142?

**Jawaban:**  
Basis data `information_schema` tetap terlihat karena merupakan basis data sistem standar (*read-only*) yang memuat metadata mengenai skema, tabel, tipe kolom, dan hak akses yang wajib dibaca oleh setiap pengguna yang berhasil login. Sedangkan perintah `USE mysql;` menghasilkan `ERROR 1044 (42000)` karena basis data `mysql` menyimpan tabel kredensial autentikasi pengguna dan hak administratif global yang diisolasi ketat dari pengguna non-root.

* **Perbedaan Kode Galat:**
  * **ERROR 1045:** Galat autentikasi kredensial (koneksi awal ditolak karena nama pengguna salah, kata sandi salah, atau kata sandi tidak disertakan).
  * **ERROR 1044:** Galat otorisasi tingkat basis data (koneksi berhasil, namun pengguna tidak memiliki hak untuk memilih atau menggunakan objek basis data yang diminta).
  * **ERROR 1142:** Galat otorisasi tingkat tabel atau perintah spesifik (pengguna dapat mengakses basis data, namun dilarang mengeksekusi aksi tertentu, contohnya akun tamu yang mencoba mengeksekusi `CREATE TABLE` padahal hanya diberikan izin `SELECT`).

### Titik Analisis 4
**Soal:**  
Mode `cookie` meminta pengguna mengetik password setiap kali masuk. Mengapa mode ini lebih aman daripada mode `config` yang menyimpan password di dalam berkas konfigurasi?

**Jawaban:**  
Mode `cookie` jauh lebih aman karena menerapkan proses validasi autentikasi aktif pada setiap sesi penjelajahan. Kredensial tidak tersimpan permanen di server melainkan didekripsi sementara melalui sesi terenkripsi yang memiliki batas waktu (*session timeout*). Sebaliknya, mode `config` menyimpan kata sandi dalam bentuk teks polos (*plain text*) di dalam berkas skrip `config.inc.php`. Apabila ada pihak lain yang memiliki akses fisik atau celah akses baca ke direktori server web, pihak tersebut dapat langsung membaca kata sandi dan mengambil alih kendali basis data sepenuhnya.
